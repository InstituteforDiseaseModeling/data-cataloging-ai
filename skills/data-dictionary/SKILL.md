# Generate Data Dictionary

Use this skill when the user wants to generate variable-level metadata for a dataset.

This skill creates a human-reviewable data dictionary describing each column in a dataset, including labels, descriptions, data types, allowed values, missingness, examples, and confidence levels.

## When to use this skill

Use this skill when the user asks to:

* Generate a data dictionary
* Create a codebook
* Describe dataset columns
* Produce variable-level metadata
* Explain what each column likely means
* Prepare column metadata for a catalog, README, or metadata package

## Inputs

The user may provide one or more of the following:

* A dataset file
* A dataset profile generated by the Profile Dataset skill
* Existing metadata
* Existing documentation, such as a README, protocol, survey instrument, schema, or codebook
* Domain context from the user
* Naming conventions or internal standards

## Outputs

Generate a data dictionary with one row per column.

The standard output should include:

| Field                   | Description                                |
| ----------------------- | ------------------------------------------ |
| variable_name           | Original column name                       |
| suggested_label         | Human-readable column label                |
| description             | Plain-language explanation of the variable |
| inferred_type           | Inferred data type                         |
| role                    | Likely role of the field                   |
| allowed_values_or_range | Valid values, categories, or numeric range |
| missing_value_notes     | Missingness and missing-value conventions  |
| example_values          | Small set of representative examples       |
| quality_notes           | Data quality or interpretation notes       |
| sensitivity_notes       | Privacy, sensitivity, or access concerns   |
| confidence              | high, medium, or low                       |
| needs_review            | true or false                              |

## Required behavior

When generating a data dictionary:

* Preserve original column names exactly.
* Generate clear, concise human-readable labels.
* Use observed values to support descriptions whenever possible.
* Use existing documentation over inference when documentation is provided.
* Clearly distinguish documented facts from AI-inferred descriptions.
* Include confidence levels for inferred descriptions.
* Mark ambiguous variables as needing human review.
* Flag potentially sensitive variables.
* Avoid overclaiming meaning based on column names alone.
* Avoid exposing sensitive row-level values.
* Use plain language that a dataset user can understand.

## Variable roles

Assign one or more likely roles where applicable:

* identifier
* date
* time
* geography
* categorical variable
* numeric measure
* binary indicator
* free text
* outcome
* exposure
* covariate
* weight
* denominator
* numerator
* model parameter
* model output
* metadata field
* unknown

If uncertain, use `unknown` or mark the role as low confidence.

## Type inference

Use these standard type labels unless the user provides another schema:

* string
* integer
* float
* boolean
* date
* datetime
* categorical
* geometry
* json
* array
* unknown

Do not infer a type based only on the first few rows if more data is available.

## Suggested labels

Create labels by:

* Expanding abbreviations where reasonably clear
* Replacing underscores or camelCase with readable words
* Preserving domain-specific terms when appropriate
* Avoiding unsupported assumptions

Examples:

* `admin1_name` → `Administrative level 1 name`
* `facility_id` → `Facility identifier`
* `cp_rate` → `Contraceptive prevalence rate`, only if context supports that meaning
* `run_id` → `Model run identifier`

If an abbreviation is unclear, mark the label as needing review.

## Descriptions

Descriptions should answer:

* What does this variable represent?
* What is the unit of observation?
* How should the value be interpreted?
* Are there known restrictions, caveats, or dependencies?

Descriptions should be concise, usually one sentence.

Example:

```text
Unique identifier for the health facility associated with the record.
```

For low-confidence fields, use cautious language:

```text
Likely indicates the reporting period for the record; confirm whether this refers to collection date, reporting date, or event date.
```

## Allowed values and ranges

For categorical variables, include observed categories when the list is short.

For numeric variables, include:

* Minimum value
* Maximum value
* Whether values appear continuous or discrete
* Units, if known or inferable

For date variables, include:

* Earliest observed date
* Latest observed date
* Date format
* Granularity

For high-cardinality text fields, summarize rather than list all values.

## Missing value notes

Report:

* Number and percent missing, if available
* Observed missing-value markers
* Whether missingness appears meaningful
* Any suspicious placeholder values

Examples of missing-value markers:

* blank
* NA
* N/A
* null
* Unknown
* Other
* 999
* -99

## Sensitivity notes

Flag variables that may contain:

* Names
* Email addresses
* Phone numbers
* Physical addresses
* Person identifiers
* Household identifiers
* Exact GPS coordinates
* Sensitive health information
* Demographic characteristics
* Small-area geography
* Partner-restricted or internal-only information
* Free-text notes that may contain sensitive content

Use cautious phrasing. Do not make final governance decisions.

## Confidence scoring

Use:

* High: supported by documentation or strongly supported by column name and values.
* Medium: likely interpretation, but not explicitly documented.
* Low: ambiguous, abbreviation unclear, or values do not provide enough evidence.

## Review flags

Set `needs_review: true` when:

* The variable meaning is ambiguous
* The variable may be sensitive
* The variable appears to be an identifier
* Units are unclear
* Categories are coded but not labeled
* The description is based primarily on inference
* The variable has unexpected values or quality issues
* There are multiple plausible interpretations

## Preferred output formats

Default to markdown table for readability.

If the user plans to save or reuse the output, also provide CSV-compatible or YAML-compatible structure.

Example YAML:

```yaml
data_dictionary:
  - variable_name:
    suggested_label:
    description:
    inferred_type:
    role:
    allowed_values_or_range:
    missing_value_notes:
    example_values:
    quality_notes:
    sensitivity_notes:
    confidence:
    needs_review:
```

Example markdown table:

| variable_name | suggested_label | description | inferred_type | role | allowed_values_or_range | missing_value_notes | confidence | needs_review |
| ------------- | --------------- | ----------- | ------------- | ---- | ----------------------- | ------------------- | ---------- | ------------ |

## Human review section

End with a section called `Recommended human review`.

Include:

* Ambiguous variables
* Sensitive variables
* Variables with unclear units
* Variables with coded categories that need labels
* Variables whose descriptions depend on domain context
* Variables that should be checked against existing documentation

## Do not do the following

Do not:

* Rename columns unless explicitly asked.
* Remove columns from the data dictionary.
* Invent units, labels, or coding schemes.
* Treat inferred descriptions as confirmed facts.
* Include long lists of raw values for high-cardinality or sensitive columns.
* Ignore existing documentation when it conflicts with inference.
* Make final access, privacy, or compliance decisions.
